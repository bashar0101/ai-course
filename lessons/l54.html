التكلفة

السعر لكل مليون رمز، ورموز الجواب أغلى من رموز الطلب عادة:

cost=nin106×pin+nout106×pout

والأسعار تتغير، وتختلف بين النماذج. راجع صفحة الأسعار عند المزود دائماً. في الأمثلة هنا أسعار افتراضية للتوضيح فقط.

مثال محلول باليد
كم تكلّف محادثة؟
أسعار افتراضية

3 دولارات لكل مليون رمز في الطلب، و 15 لكل مليون رمز في الجواب.

طلب واحد

ألفا رمز في الطلب، وخمسمئة في الجواب:

2000106×3+500106×15=0.006+0.0075=0.0135

أقل من سنتين. لكن عشرة آلاف طلب في اليوم: 135 دولاراً يومياً.

محادثة من عشر جولات

في كل جولة: المستخدم يكتب 100 رمز، والمساعد يرد بـ 200. والواجهة بلا حالة، فكل طلب يحمل كل ما قبله.

طلب الجولة t فيه: رسائل المستخدم حتى الآن، 100 t، وأجوبة المساعد السابقة، 200 (t−1):

nin(t)=100 t+200 (t−1)=300 t−200
الجولة12310
رموز الطلب1004007002800

المجموع للجولات العشر:

∑t=110(300 t−200)=300×55−2000=14,500

المستخدم كتب ألف رمز فقط، لكننا دفعنا ثمن 14,500 رمز طلب!

التكلفة: 0.0435 للطلبات، و 0.03 للأجوبة. المجموع حوالي 7 سنتات.

المحادثات الطويلة تكلف أكثر بكثير مما تبدو. والعربية تأخذ رموزاً أكثر غالباً، كما رأينا في الدرس 43.

طرق لتقليل التكلفة:

  • اختر أصغر نموذج يؤدي المهمة جيداً.
  • لخّص المحادثات الطويلة بدل إرسالها كاملة.
  • بعض المزودين يخزّن بداية الطلب المتكررة، مثل رسالة نظام طويلة، بسعر أقل.
  • الطلبات غير العاجلة يمكن إرسالها دفعة واحدة بسعر أقل.

الأدوات

النموذج لا يعرف الطقس الآن، ولا يرى قاعدة بياناتك. لكنك تستطيع أن تعطيه أدوات: دوال من برنامجك، مع وصف ومخطط لمدخلاتها.

الدورة:

  1. ترسل السؤال، مع وصف الأدوات.
  2. النموذج يرد بطلب أداة: الاسم، والمدخلات. وسبب التوقف: يطلب أداة.
  3. برنامجك يشغّل الدالة فعلاً.
  4. ترسل النتيجة للنموذج، فيكمل ويكتب الجواب.
tool use · tool_use · tool_result
النموذج لا يشغّل أي شيء بنفسه. هو يطلب، وبرنامجك يقرر وينفذ. لذلك تحقق دائماً من المدخلات قبل التنفيذ، خصوصاً مع أي عملية تغيّر بيانات.

والأدوات تحل مشكلة أخرى: المخرجات المنظمة. إذا أردت كائناً بحقول محددة، عرّفه كمدخلات أداة، واطلب من النموذج استخدامها. فيأتي الجواب غالباً مطابقاً للمخطط. ومع الخيار الصارم في تعريف الأداة، تضمن الواجهة المطابقة.

"strict": true

والواجهة تقبل أيضاً مخطط جيسون مباشرة، في إعدادات المخرجات، فيلتزم الجواب كله بالمخطط. سنستخدمه في الدرس 57.

لكي يعمل الكود بدون مفتاح أو إنترنت، نشغّل خادماً محلياً صغيراً يتظاهر أنه الواجهة: يسجل الطلب، ويرجع رداً جاهزاً بنفس الصيغة.

fake_server.pyبايثون
import json
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer

class FakeAPI(BaseHTTPRequestHandler):
    replies = []            # queue of (status, json) the server will answer with
    received = []           # every request it got

    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        FakeAPI.received.append({"path": self.path, "version": self.headers.get("anthropic-version"), "body": body})
        status, reply = FakeAPI.replies.pop(0)
        data = json.dumps(reply).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def log_message(self, *args):
        pass

server = HTTPServer(("127.0.0.1", 0), FakeAPI)
threading.Thread(target=server.serve_forever, daemon=True).start()
FAKE_URL = f"http://127.0.0.1:{server.server_port}"

def fake_text_reply(text, n_in, n_out):
    return 200, {"id": "msg_fake", "type": "message", "role": "assistant", "model": "fake",
                 "content": [{"type": "text", "text": text}], "stop_reason": "end_turn",
                 "stop_sequence": None, "usage": {"input_tokens": n_in, "output_tokens": n_out}}
print("fake API listening on", FAKE_URL)

من تطبيق سبرنغ بوت

خدمة صغيرة ترسل الطلب من الخادم، وتقرأ الجواب. بالعميل المدمج في سبرنغ، بدون أي مكتبة إضافية. الكود لسبرنغ بوت 3.2 أو أحدث:

ClaudeClient.javaجافا
import java.util.List;
import java.util.Map;
import org.springframework.http.MediaType;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestClient;

@Service
public class ClaudeClient {

    // only the fields we read from the response
    record Block(String type, String text) {}
    record Reply(List<Block> content) {}

    private final RestClient rest = RestClient.builder()
            .baseUrl("https://api.anthropic.com/v1")
            .defaultHeader("x-api-key", System.getenv("ANTHROPIC_API_KEY"))
            .defaultHeader("anthropic-version", "2023-06-01")
            .build();

    public String ask(String question) {
        Map<String, Object> body = Map.of(
                "model", "claude-haiku-4-5-20251001",
                "max_tokens", 500,
                "messages", List.of(Map.of("role", "user", "content", question)));
        Reply reply = rest.post()
                .uri("/messages")
                .contentType(MediaType.APPLICATION_JSON)
                .body(body)
                .retrieve()
                .body(Reply.class);
        return reply.content().stream()
                .filter(b -> "text".equals(b.type()))
                .map(Block::text)
                .findFirst()
                .orElse("");
    }
}

نقرأ الرد في سجلات صغيرة فيها الحقول التي نحتاجها فقط، والباقي يُتجاهل. هكذا يعمل الكود مع إصدارات مكتبة جيسون المختلفة، ولا ينكسر إذا جاء الرد بلا نص.

المفتاح يُقرأ من متغير بيئة على الخادم، والمتصفح لا يراه أبداً. ويوجد أيضاً عميل رسمي بلغة جافا، إذا أردت أنواعاً جاهزة بدل التعامل مع الحقول بيدك.

الثقة بالجواب كأنه كود

الجواب نص يولّده نموذج. قد يكون الشكل خاطئاً، أو الحقل ناقصاً، أو الرقم مخترعاً.

تحقق من المخرجات قبل استخدامها: حلّل الصيغة، وتحقق من الحقول، وضع حدوداً للقيم. ولا تنفذ أي أمر يطلبه النموذج بدون فحص.

سؤال مقابلة

سؤال قد تسمعه في المقابلة:

The API is stateless. How do you build a multi-turn chat on top of it?

جواب قصير وجيد:

The client or backend stores the conversation history and sends all previous user and assistant messages with every request. Because input tokens grow with each turn, long conversations are usually truncated, summarized, or trimmed to the most relevant parts to control cost and stay within the context window.

سؤال قد تسمعه في المقابلة:

How does tool use (function calling) work?

جواب قصير وجيد:

You describe tools with a name, a description and a JSON schema for their inputs. When the model decides a tool is needed, it stops with a tool-use block containing the tool name and arguments. Your code validates and executes the function, then sends the result back in a tool-result block that references the call id, and the model continues. The model never executes anything itself.

سؤال قد تسمعه في المقابلة:

How would you make an LLM integration robust in production?

جواب قصير وجيد:

Keep the API key server-side, set timeouts, retry transient errors such as rate limits with exponential backoff, validate and parse outputs against a schema, log token usage for cost monitoring, add fallbacks for failures, and test the integration with mocked responses so tests are fast and free.

الخلاصة
  • الواجهة البرمجية تعطيك أقوى النماذج بلا كرت شاشة، وتدفع حسب الرموز.
  • الطلب: النموذج، والحد الأقصى، ورسالة النظام، والرسائل. والرد: المحتوى، وسبب التوقف، والاستخدام.
  • الواجهة بلا حالة: كل طلب يحمل المحادثة كلها، فالتكلفة تكبر بسرعة مع طول المحادثة.
  • المفتاح في متغير بيئة على الخادم فقط.
  • الأدوات: النموذج يطلب، وبرنامجك ينفذ ويرجع النتيجة. وتصلح للمخرجات المنظمة أيضاً.
  • الأخطاء المؤقتة تحتاج إعادة محاولة بانتظار يتضاعف.
  • اختبر كودك بخادم مزيف: سريع ومجاني.

تمرين: محادثة أرخص

محادثة من عشرين جولة: المستخدم يكتب 150 رمزاً في كل جولة، والمساعد يرد بـ 300. والأسعار الافتراضية: 3 و 15 دولاراً لكل مليون.

  1. اكتب قانون رموز الطلب في الجولة t، واحسب مجموع رموز الطلب للجولات العشرين.
  2. احسب التكلفة الكلية.
  3. فكرة للتوفير: في كل طلب، أرسل آخر أربع جولات كاملة فقط. احسب مجموع رموز الطلب الجديد، ونسبة التوفير.
تلميح

مع الفكرة الثالثة، الجولة t فيها رسائل المستخدم والمساعد من آخر أربع جولات سابقة على الأكثر، ثم رسالة المستخدم الجديدة.

الحل (افتحه بعد أن تحاول)
  1. قانون رموز الطلب في الجولة t:
nin(t)=150 t+300 (t−1)=450 t−300

والمجموع للجولات العشرين:

450×210−300×20=94,500−6,000=88,500
  1. الطلبات: 88,500×3/106≈0.266. والأجوبة: 20×300×15/106=0.09. المجموع حوالي 0.356 دولار.
  1. الجولة t تحمل min⁡(t−1,4) جولات سابقة، كل واحدة 150+300=450 رمزاً، زائد 150 للرسالة الجديدة.
بايثون
full = sum(450 * t - 300 for t in range(1, 21))
window = sum(450 * min(t - 1, 4) + 150 for t in range(1, 21))
print(full, window, f"saving {1 - window / full:.0%}")
print(f"cost full: {full * 3 / 1e6 + 20 * 300 * 15 / 1e6:.3f}  cost with window: {window * 3 / 1e6 + 20 * 300 * 15 / 1e6:.3f}")

1. قانون رموز الطلب في الجولة $t$:

$$n_{in}(t) = 150 \, t + 300 \, (t - 1) = 450 \, t - 300$$

والمجموع للجولات العشرين:

$$450 \times 210 - 300 \times 20 = 94{,}500 - 6{,}000 = 88{,}500$$

2. الطلبات: $88{,}500 \times 3 / 10^6 \approx 0.266$. والأجوبة: $20 \times 300 \times 15 / 10^6 = 0.09$. المجموع حوالي 0.356 دولار.

3. الجولة $t$ تحمل $\min(t - 1, 4)$ جولات سابقة، كل واحدة $150 + 300 = 450$ رمزاً، زائد 150 للرسالة الجديدة.

full = sum(450 * t - 300 for t in range(1, 21))
